# MinScript

MinScript is a language that aims for TypeScript-style concision, Rust-style ownership (with no lifetime annotations) and Go-style simplicity. This folder is the spec-first restart. The deterministic, hand-written TypeScript lexer (`src/lexer.ts`) and the recursive-descent + Pratt parser (`src/parser.ts`) name resolution (`src/resolve.ts`, single package) a first type checker (`src/check.ts`, spec §9.12) a first ownership pass (`src/ownership.ts`, spec §9.13) lowering to HIR (`src/lower.ts`, spec §14.1) a first JS back end (`src/js/`, spec §14.2: `npm run run -- file.ms`), package loading (`src/loader.ts`, spec §8.1), the first std packages (`std/*/`, spec §10.4) and projects (`mod.ms` evaluated by `src/project.ts`, spec §17: `npm run run -- test/projects/basic`, `npm run config -- dir`) are done. Next candidates: registry/git dependencies and `mod.lock`, the §17.5 sandbox, `std.net.http`, more std, and the JS gaps listed in §14.2.

## Boundaries

- Work only inside `min_script/minscript/`. **Never modify files in the parent `min_script/` folder** (`cmd_ts/`, `ms_cmd_ts/`, `samples/`, `docs/`). Reading them for reference is fine.

## Layout

- `docs/spec.md`: **the source of truth** (v0.2 unified spec). Change the spec before or alongside any syntax change, and keep §0.1 (change log), §11 (diagnostics), §12 (EBNF), §13 (corpus) and §18 (open questions) in sync.
- `docs/spec-v1.rs`, `spec-v2.rs`, `merge_1.rs`, `notes_1.md`, `docs/history/samples/`: superseded and old-syntax material. Keep it for history, and don't update it.
- `src/`: the compiler in TypeScript, run directly by Node ≥ 23.6 (type stripping). There are no runtime dependencies, and the only dev dependencies are `typescript` and `@types/node`.
  - Write erasable TS only: no `enum`, `namespace` or parameter properties. Import with `.ts` extensions.
  - `token.ts`, `diagnostic.ts`, `lexer.ts`, `dump.ts` (token dump / `.tokens` format), `ast.ts`, `parser.ts`, `sexpr.ts` (AST dump / `.ast` format), `resolve.ts`, `resolve_dump.ts` (`.refs` format), `std_stub.ts`, `prelude.ts`, `types.ts`, `check.ts`, `check_dump.ts` (`.types` format), `ownership.ts`, `hir.ts`, `lower.ts`, `hir_dump.ts` (`.hir` format), `hir_check.ts` (HIR validator), `loader.ts` (loads a program's packages and runs every pass on each, in dependency order), `project.ts` (finds and evaluates `mod.ms`), `project_cli.ts` (`run` / `js` / `config`), `cli.ts`, and `js/` (`emit.ts` HIR → JS, `runtime.ts` the runtime, `run.ts` compile + run).
  - The prelude is MinScript: `std/prelude.ms` (bodies are `_builtin()`). Add prelude APIs there, not in TypeScript; it must parse, resolve and type-check cleanly.
  - Std packages are folders under `std/` (`std/net/ws/ws.ms` is `std.net.ws`), written in MinScript. A function whose body is only `_builtin()` is provided by the runtime under its package name (`$rt.std["json.parse"]`, `$rt.std["net.ws.Writer.send"]`); everything else in std is compiled. A new builtin needs a runtime entry, and every std package must load cleanly (corpus test).
  - `run`, `js` and the language server go through the loader; `check`, `hir`, `resolve` treat each file as its own package, so imported members are `unknown` there (gradual, never reported). Don't add workarounds for that in the checker. Unit tests sit next to the code as `*.test.ts` (node:test).
  - Commands: `npm test`, `npm run test:update` (rewrites `.tokens` / `.ast` snapshots, so review the diff), `npm run typecheck`, `npm run lex -- file.ms`, `npm run parse -- file.ms`, `npm run resolve -- file.ms`, `npm run check -- file.ms`, `npm run hir -- file.ms`, `npm run js -- file.ms`, `npm run run -- file.ms`.
  - Passes don't modify the AST: the resolver (and later the type checker) return side tables keyed by AST node; lowering will build a new tree (HIR).
  - Keep spec §1, §5.4, §8.7, §9.12, §9.13, §11, §12 and §14 in sync with the passes.
  - The JS runtime implements prelude methods by name (`$rt.std["Vec.push"]`); a new prelude method in `std/prelude.ms` needs a runtime entry too. Add behaviour tests as `test/run/*.ms` with a `.out` snapshot.
  - Lowering reads the checker's recorded decisions (`calls`, `members`, `variants`, `rets` in `CheckResult`); it never re-derives type rules. If lowering needs a fact, record it in the checker.
  - MinScript samples must also pass the ownership rules: `var` for anything mutated, `.clone()` to move out of a borrow (including `for x in items` items), `#[x]` for closures that escape. A new lexer diagnostic code goes in `LEXER_CODES` too.
  - Parser errors: use `report()` when the intended form is clear (then keep parsing), and `fail()` otherwise (it reports and syncs to the next statement, item, member or arm). Each mistake must produce exactly one diagnostic, and every `errors/` file must match its `//~` annotations exactly.
- `tools/`: editor tooling. See `tools/vscode/README.md`.
  - `tools/vscode/`: the VS Code extension. The grammar is generated by `syntaxes/build-grammar.py` (edit the script, not the JSON); `npm test` there checks it with the real TextMate engine.
  - `tools/lsp/`: the language server. `analysis.ts` answers queries from the compiler's results, and `server.ts` is the LSP wrapper. It is tested by the root `npm test`.
  - When the syntax changes (spec §1), update the grammar too. When a pass starts recording new facts, the LSP can usually show them through `analysis.ts`.
- `test/`: corpus. See `test/README.md`. `test/corpus.test.ts` runs it.
  - `lexer/`, `parser/`: one feature per file. Expected-output snapshots (`.tokens` / `.ast`) come later, once the lexer and parser can generate them.
  - `errors/`: one case per function, with `//~ CODE` on the line where the diagnostic is expected.
  - `programs/`: realistic programs that must parse with zero diagnostics.
  - `projects/`: projects with a `mod.ms` (or a plain folder of `package main` files). Each must evaluate (`config.json`) and run (`run.out`, which includes `task` scripts' output).
  - `packages/`: programs of several packages; each `main.ms` is loaded with its imports. With `//~` annotations in any of its files they must match; otherwise it runs and prints its `main.out`.

## Writing MinScript code (samples, tests, spec examples)

- **Balance the binding styles.** Mix `let`/`var` and `:=`/`:==` evenly so they complement each other, and don't let either take over.
  - `:=`/`:==` suit quick locals, counters, intermediates and `x := [] as Vec[T]`.
  - `let`/`var` suit type annotations, patterns (`let t(a, b) = …`, `let … else`) and declarations that stand out.
- **`as` is also a type annotation:** `g := [] as Vec[Map[string, int]]` is as valid as `let g: Vec[Map[string, int]] = []`. The user likes the value-first form, so use both.
- Follow v0.2 syntax:
  - closures are `#{…}` / `#[x, &mut y]{…}` (never `(a) => …`);
  - type generics are `Vec[T]`, explicit call generics are `f.[T](x)` (never `<T>`);
  - sum types are `union X = { A  B(T) }`; loops use `for` only;
  - Vec literals are `[]`; fallbacks use `??`; owned strings come from `to_str()`;
  - methods may be written inline in `type`/`union` bodies;
  - `log` is in the prelude, while `println` needs an import.
  - Inter-task communication uses `Topic` (broadcast), `Queue` (one consumer), `Signal` (state), `Promise.new()` (one-shot), `select { … }` and `for await` (spec §4.9, §9.10). There are no channels.
  - Handles (`Ref`, `Topic`, `Queue`, `Signal`) clone implicitly, so never write `.clone()` on them. Subscriptions are `Sub[T]`.
  - Variants are inferred from the expected type: write `send(Text("hi"))` and `-> Shape { Empty }`; the qualified `Message.Text` stays valid.
  - `map[k] = v` inserts or overwrites. `Ref.read` and `Ref.update` return the closure's value. Owned interface values are boxed implicitly, so don't write `Box[Inter]`.
  - Avoid the self-wait: don't `for await` over a subscription in the same task that keeps its topic open until after the loop (`L_SELF_WAIT`).
- Code should be valid against `docs/spec.md`. If you find a gap or contradiction while writing an example, fix the spec too and say so.
